# Roadmap

What could come after the first iteration, in a likely order. Each item says what it adds and what it would change in the design. Nothing here is built.

1. **Capture, void and refunds.** Authorization and capture as separate steps, an automatic void of authorizations that are never captured, and partial refunds. Each call to the acquirer becomes an operation row, written before it is sent, as attempts are today.
2. **SLOs.** Objectives with error budgets on top of the metrics of ADR 0006, the consumers' lag on Kafka, and alerts routed to someone on call.
3. **Throughput.** On one machine, the load test of step 9 held 500 payments per second near the edge of NFR01: in one run of two, the tail came from requests waiting for the API's database connections, in a Postgres that shares Docker Desktop with the whole stack (README, "Proof"). Beyond it: Postgres on a host of its own with fast storage, several API instances behind a load balancer (each caps its own payments in flight), a short cache of API keys so a request does not read the merchant every time, batched inserts in the webhooks consumer, and sampled traces.
4. **Risk.** Velocity limits per card and per IP, blocklists and card-testing detection. They run inside the request, before the authorization, so they keep working when Kafka is down.
5. **Merchant portal.** Login, users with roles, API key rotation, webhook endpoints managed by the merchant, and resending events.
6. **A second acquirer, with safe failover.** Routing by card brand, cost and health. Health becomes a failure rate over a window, for the breaker too: the breaker of this iteration counts failures in a row, and under load it opened by chance with a third of the calls failing (README, "Proof"). Failing over is only safe once the first acquirer certainly holds no live authorization: after a refused connection, or after a confirmed reversal. A TLA+ model of that protocol was started on the `spec/authorization-model` branch. Writing it found the need for reversals recorded before they are sent, epochs that fence out stale workers, and tombstones at the acquirer; this iteration's design already includes all three.
7. **Money: ledger, settlement and payouts.** A double-entry ledger fed by the payment events, settlement files from the acquirer reconciled against the payments and the bank, and payouts per merchant with a cut-off time. This is where another consumer of the payment events adds the most.
8. **Production.** Kubernetes, three Kafka brokers, a Postgres primary with replicas, chaos tests and recovery drills.
